### 2.2 展开版本（推荐理解每步在干什么）

```bash
# 第 1 步：基础链路 = robot_state_publisher + 雷达 + 里程计
#   ⚠️ robot_base.launch.py 内部已经 include 了 lidar.launch.py，不要再单独起雷达，
#      否则两个驱动进程抢 /dev/ttyUSB0，日志刷 "Check Sum ..." 错、/scan 出现两个发布者。
ros2 launch robot_bringup robot_base.launch.py odom_source:=chassis

# 第 2 步：SLAM（另开终端）
ros2 launch robot_bringup slam.launch.py mode:=mapping rviz:=false

# 第 3 步：遥控逛一圈（再开终端）
ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -p speed:=0.3 -p turn:=0.5
#   ⚠️ 不要加 --repeat：本板 teleop_twist_keyboard 是 2.4.1，没有这个参数，加了会
#      UnknownROSArgsError 秒退（现象 = screen -r teleop 报 no screen to resume）→ 见坑 18
#   改「按住方向键」：终端自动重复发键就是 10Hz 级别，足以压住底盘 0.5s 看门狗

# 第 4 步：存图（逛完、车停稳，等 ≥5s 让地图推送一轮）
ros2 run nav2_map_server map_saver_cli -f /home/sunrise/Robot/ros2_car/maps/my_map3
```

> `~/tools/nav_screen.sh` 就是把这四步装进 screen 会话（ssh 断开不掉进程），行为与上面完全一致，只是 `base` 不带参数时默认 `fused`，建图请显式写 `base chassis`。

### 2.3 里程计源怎么选（重要）

`odom_source` 三选一：

| 取值 | 含义 | 何时用 |
|---|---|---|
| `chassis` | STM32 轮速编码器 → `/odom`，由 `odom_to_tf` 发 TF | **建图/导航首选（本手册主线，已实机验证）** |
| `rf2o` | 激光里程计兜底，无底盘时用 | 底盘没接、只想验证雷达链路 |
| `fused` | 轮速 + rf2o（+ 新固件的 IMU `vyaw`）过 EKF，`odom→base_link` 由 EKF 独发 | 打滑严重、要更稳的里程计时（**尚未跑完整 Nav2 导航链路**） |

**实测结论（2026-09-11）**：原地自转时 `chassis` 报 Δyaw≈154°（指令 172°，方向正确），而 `rf2o` 只报 4°——**2D 扫描匹配在纯旋转下退化**，所以建图/导航用 `chassis`（或 `fused`），不要用纯 `rf2o` 跑自转。

**2026-09-13 补充（fused 的现状）**：EKF 的**航向只由 IMU 负责**（`odom1_config` 关 yaw、`imu0` 差分融 yaw+vyaw），rf2o 只贡献 x/y 平移。板卡实测：静止漂移 −0.0002°/s、架空空转时 `/odom_filtered` 只被轮速带偏 2.5%。**前提=固件是新固件**（上行 0x83、`/imu` 存在）；IMU 不在时 fused 仍能起，只是航向回到轮速+激光。改 `ekf_params.yaml` 后必须 `rm -rf build install` 重建（坑 14）。

> TF 红线（REP-105）：`odom→base_link` 只能有一个发布者。`chassis` 模式由 `chassis_driver` 发；`fused` 模式由 EKF 发（此时驱动 `publish_tf:=false`）。改动前看 `ROS2导航调试经验.md`。

### 2.4 建图的正确姿势

1. **别贴墙**：车贴墙时原地转会被甩尾顶住打滑，图会建歪。四周留 ≥0.5m（用 `zone_clearance.py` 量）。
2. **小步走**：麦轮底盘原地自转有滑移，每走 0.3~0.5m 停一下，让它扫几帧再继续。
3. **绕回起点**：走一个闭环（例如沿房间绕一圈回到出发位置附近），`do_loop_closing: true` 会把图对齐回来，比不闭合的图准确得多。
4. **地图 5s 才推一次**：`slam_toolbox_params.yaml` 的 `map_update_interval: 5.0`，所以两次存图间隔 <5s 时**内容必然相同，那不是"卡住"**。
5. **不要频繁重启节点**：建图途中反复 `kill base` / 占用串口，会让 slam_toolbox 的 message filter 队列积压（日志刷 `queue is full`）而丢帧；真丢帧了就重启 `slam` 会话清空队列。
6. **起始点尽量在地图中间**：导航时 AMCL 默认初始位姿是 (0,0,0)，建图起点越接近开阔处越好对齐（见 §3.3）。

### 2.5 怎么判断图在长（别被假象骗）

- ✅ 可靠：`python3 ~/tools/map_hash_probe.py --secs 30` —— 打印每帧 `/map` 的栅格 md5、已知格数、占用格数，**这些数字在变才是真的在更新**
- ✅ 可靠：`python3 ~/tools/map_progress_check.py --tag t1` —— 存图并打 md5（两次之间必须 >5s 且车动过）
- ❌ 不可靠：看 `/map` 的 `info.map_load_time` —— Humble 的 slam_toolbox 里它**恒为 0**，据此判断会得出"地图没更新"的错误结论
- ❌ 不可靠：只看地图 width/height 不变就认为卡住（原地转圈时边界本来就可能不变）


**换地图只需改一个参数**（⚠️ **2026-09-13 修正**：此前本文写的"要改两处"是错的）：

```bash
~/tools/nav_screen.sh nav my_map3       # ← 换图就换这一个参数；名字 / 名字.pgm / 名字.yaml / 绝对路径都行

```

手动起 launch 时同理，**必须显式传** `map:=`：

```bash

  map:=/home/sunrise/Robot/ros2_car/maps/my_map3.yaml rviz:=false autostart:=false
```

**为什么不再需要改 `nav2_params.yaml`**：`map:=` 会经 nav2_common 的 `RewrittenYaml` **递归改写** `yaml_filename`（它遍历整棵参数树的叶子键，`map_server.ros__parameters.yaml_filename` 也在内），所以 AMCL 与 `map_server` 拿到的是**同一张图**；`nav2_params.yaml` 里那行 `yaml_filename` 在走 launch 时**被覆盖、不生效**。板上实测证据（只读探针，2026-09-13）：

```bash
# 用 RewrittenYaml 模拟 launch 的替换，传 map=/tmp/PROBE_AAA.yaml，打印生成参数：
#   -> yaml_filename: /tmp/PROBE_AAA.yaml
```

⚠️ **反向的坑**：既然 `map:=` 一定会覆盖，那**不传 `map:=` 就一定加载不到想要的图**——launch 的 `map` 默认值指向 `install/robot_bringup/share/robot_bringup/maps/my_map.yaml`，而仓库 `src/robot_bringup/maps/` 里只有 README，是条**死路径**。`nav_screen.sh nav` 现在会在启动前校验地图文件存在，不存在直接报错并列出可用地图（不再静默起一个加载不到图的 Nav2）。

## 3. 启动导航（Nav2 自主导航）

### 3.1 关键前提：**不要用 `bringup.launch.py mode:=navigation`**

双层 include 下 nav2 的 `RewrittenYaml` 会丢 `map` 参数 → `map_server` 报 `yaml_filename is not initialized`、controller 报 `No critics defined`。必须**分步起**。

### 3.2 标准三步（板卡上无头运行）

```bash
source /opt/ros/humble/setup.bash
source ~/ros2/yahboomcar_ws/install/setup.bash
source /home/sunrise/Robot/ros2_car/install/setup.bash
export ROS_LOG_DIR=/home/sunrise/Robot/.diag/roslog

# ① 基础链路（雷达 + 底盘里程计 + TF）
ros2 launch robot_bringup robot_base.launch.py odom_source:=chassis

# ② Nav2：rviz 关掉、autostart 关掉（慢板卡上并行 autostart 会竞态）
ros2 launch robot_bringup navigation.launch.py \
  map:=/home/sunrise/Robot/ros2_car/maps/my_map.yaml rviz:=false autostart:=false

# ③ 按依赖顺序手动激活生命周期节点（bt_navigator 放最后，要几分钟耐心等）
python3 /home/sunrise/Robot/ros2_car/tools/activate_nav.py
```

`activate_nav.py` 会依次 configure/activate `map_server → amcl → controller_server → smoother_server → planner_server → behavior_server → waypoint_follower → velocity_smoother → bt_navigator(最后)`，并等 `/follow_path`、`/backup` 等动作服务就绪。**必须 bt_navigator 最后**：它在激活时会预加载整棵 BT 并检查动作服务，1s 窗口内没就绪就失败（Humble 无法配长这个窗口）。

激活成功的标志：

```bash
ros2 action list | grep navigate_to_pose     # 应该有 /navigate_to_pose
ros2 lifecycle get /bt_navigator             # active
```

### 3.3 设置初始位姿（AMCL 必须，否则不会动）

`nav2_params.yaml` 里 AMCL 是 `set_initial_pose: true` + `initial_pose: 0,0,0`。**只有"建图时小车起始位置正好是地图原点(0,0,0)"才成立**；实际往往不是，需要手动给：

- **推荐（远程可视化）**：起 rosbridge，用 Foxglove 连 `ws://100.65.82.93:9090`，3D 面板里设置初始位姿对齐地图，再发导航目标

  ```bash
  ~/tools/nav_screen.sh lat      # rosbridge，端口 9090，无鉴权，仅调试用
  # 连不上先查这三步：screen -ls 有没有 lat → ss -ltnp | grep 9090 → tail /tmp/lat.log
  # ⚠️ rosbridge 不属于 base/nav：kill all 会把它一起停掉且不会自动回来（坑 19）
  ```

- ⚠️ **不要在板卡上开 rviz2**：RDK X5 无 GPU 加速，rviz 会吃 ~410% CPU 把导航栈饿死（历史故障根因之一）。
- ⚠️ Foxglove 的 Publish 面板**不支持 action**，发目标要用其 3D 面板的导航工具，或用下面的命令行方式。

### 3.4 发目标（三种方式）

```bash
# 方式 A：命令行发 Nav2 目标（最省事，无头可用）
ros2 run robot_navigation navigate_to_pose --x 1.0 --y 0.5 --yaw 90

# 方式 B：走大模型端契约服务（navigation 模式自动带起 robot_actions 节点）
ros2 service call /robot/navigate_to robot_interfaces/srv/NavigateTo "{place: '', x: 1.0, y: 0.5, theta: 90}"
ros2 service call /robot/move  robot_interfaces/srv/Move  "{direction: forward, distance_m: 1.0}"
ros2 service call /robot/turn  robot_interfaces/srv/Turn  "{angle_deg: 90}"

# 方式 C：rviz（在别的机器上跑，别在板卡上）用 "Nav2 Goal" 工具
#   ⚠️ 不要用旧的 "2D Goal Pose"(SetGoal)——它发 /goal_pose，Nav2 不订阅，点了不会动
```

状态与急停：

```bash
ros2 topic echo /robot/exec_state          # idle / moving / navigating / error
ros2 topic echo /robot/arrived             # bool
ros2 topic pub -1 /robot/cmd_stop std_msgs/msg/Bool "{data: true}"   # 急停（取消 Nav2 + 零速）
```

### 3.5 导航不动时的排查顺序（无头验证）

```bash
ros2 topic hz /scan                                   # 雷达在不在
ros2 topic hz /odom                                   # 里程计在不在
ros2 run tf2_ros tf2_echo odom base_link              # TF 通不通
ros2 lifecycle get /bt_navigator                      # active？
ros2 topic echo /plan --once                          # 有没有规划出路径（空=没规划）
ros2 topic echo /cmd_vel --once                       # 有没有下发速度
top -bn1 | head -15                                   # 个别进程吃满 CPU（rviz 之类）会饿死导航栈
```

> 另可用 `python3 ~/tools/slam_health_probe.py`、`~/tools/time_lag_probe.py` 看 SLAM 健康度与扫描/里程计时间戳滞后。

### 3.6 导航结果的 status 码判读（含 `status=6 ❌` 的实锤）

`navigate_to_pose` / 契约服务返回的 `status` 就是 `action_msgs/GoalStatus`：**4=SUCCEEDED、5=CANCELED、6=ABORTED**（2=EXECUTING、3=CANCELING）。所以 **`status=6` = 目标被中止（ABORTED）**——不是"没跑"，而是跑了、恢复行为也跑了，但规划始终不成。

**2026-09-13 实锤案例（目标 `(1.0, 4.0)`，结果为 status=6）**：

```
[planner_server-6] [ERROR] worldToMap failed: mx,my: 44,108, size_x,size_y: 88,107
[planner_server-6] [WARN ] The goal sent to the planner is off the global costmap. Planning will always fail to this goal.
[planner_server-6] [WARN ] GridBased: failed to create plan with tolerance 0.50.
[planner_server-6] [WARN ] Planning algorithm GridBased failed to generate a valid path to (1.00, 4.00)
[behavior_server-7] [INFO ] Running backup → backup completed successfully
[behavior_server-7] [INFO ] Running spin   → spin completed successfully
[behavior_server-7] [INFO ] Running wait   → wait completed successfully
[bt_navigator-8]   [ERROR] Goal failed
```

读法：**目标点落在地图外** → 规划必然失败 → BT 依次跑恢复行为（backup 后退 / spin 自转 1.57rad / wait 5s）→ 全部无效 → `bt_navigator: Goal failed` → ABORTED。⚠️ 恢复行为**会真的让车动**（实车后退 + 原地自转，一轮约 15s），别以为"卡住不动"就去手动推车。

**发目标前先算地图有效范围**（`origin` + `size × resolution`）：

```bash
ros2 topic echo /map --once --field info     # 拿 resolution / width / height / origin
```

以 `my_map3` 实测为例：88×107 @0.05m、origin=(-1.2, -1.38) → 有效范围 **x ∈ [-1.2, 3.2]、y ∈ [-1.38, 3.97]**。目标 `(1.0, 4.0)` 的 y 只比上边界 3.97 多 **3cm**，就被判 `off the global costmap`。所以：

- 目标要**严格落在范围内并留 ≥0.3~0.5m 余量**（地图边界外全是未知/障碍）；
- 现存地图覆盖本就不足（`my_map3` 未知 60.7%），**对着 Foxglove 里的地图点目标，别照抄文档示例坐标**；
- 判失败看 nav 会话日志：`~/tools/nav_screen.sh log nav 60`，或 `grep -iE "error|fail|global costmap|abort" /tmp/nav.log`。

**⚠️ `status=4` 也必须复核位移（2026-09-13 实锤，同一晚第二次运行）**：goal checker 是 `xy_goal_tolerance: 0.25` / `yaw_goal_tolerance: 0.25`（`stateful: True`），所以"到达"可能是**容差内的宽松成功**：

| 量 | 本轮实测 |
|---|---|
| 目标 | `(0.756, 0.672)`，距起点 0.35m |
| 结束后 `/amcl_pose` | `(0.528, 0.765)` → 距目标 **0.246m**（刚好落进 0.25 容差 → 判 Reached） |
| 轮速 `/odom` 实际位移 | **0.164m** |
| `map→odom` 变换 | yaw 从 0° 变成 **65°**（AMCL 在跑动中重定位了一次） |

结论：**验收不要只看 `status`**，要同时看 ①`/odom` 位移、②实测车距、③Foxglove 里 `map→odom` 是否在跳。地图只有 60% 已知时定位精度就是这个量级；要严格验收得先重扫更完整的地图，并（可选）把容差调小复测。

## 5. 已知坑清单（照抄自实测）

1. **别用 `bringup mode:=navigation`**（丢 map 参数）→ 用 §3.2 分步。
2. **`robot_base.launch.py` 自带雷达**，不要再单起 `lidar.launch.py`，否则抢串口。
3. **雷达驱动要用本仓库的** `robot_bringup lidar.launch.py`（参数文件 `lidar_tmini_plus.yaml`，`frame_id=laser_link`）；yahboomcar 的 `ydlidar_launch.py` 默认 `TminiPro.yaml`（`laser_frame`）会与 URDF/slam 对不上。
4. **别在板卡上开 rviz2**（410% CPU 饿死导航栈）→ 用 Foxglove + rosbridge。
5. **rviz 发目标必须用 "Nav2 Goal"（GoalTool）**，不是 "2D Goal Pose"。
6. **换地图只需 `map:=` 这一个参数**（2026-09-13 修正，见 §2.6）：`map:=` 经 `RewrittenYaml` 递归改写 `yaml_filename`，`map_server` 与 AMCL 拿同一张图；`nav2_params.yaml` 里那行 `yaml_filename` 走 launch 时**不生效**。⚠️ 反过来，**不传 `map:=` 就加载不到图**（launch 默认值是条死路径）——`nav_screen.sh nav` 已加启动前校验。
7. **bt_navigator 必须最后激活**，且要等 controller/planner/behavior 的动作服务就绪。
8. **底盘 0.5s 看门狗**：遥控要**持续按键**（本板 teleop 2.4.1 无 `--repeat`；按住方向键靠终端自动重复，见坑 18），nav2 高频下发不受影响。
9. **`/scan` 是 BEST_EFFORT、`/map` 是 TRANSIENT_LOCAL**：自写订阅节点 QoS 设错会**静默收不到数据**。
10. **不要用 `pkill -f "关键词"`** 杀进程（命令自身命令行含关键词会自杀）；用 `screen -S <名> -X quit` 或 `ps | grep | awk | xargs kill`。
11. **帧/字节结构不要手工数**：用 `frame_layout_judge.py` 让 XOR 校验判定。
12. **地图更新判据**：看栅格 md5/已知格数，别看 `map_load_time`（恒 0）。
13. **启停节点一律走 `nav_screen.sh`，不要手动 `ros2 launch` 第二份**：重复起 node 会互抢 `/dev/ttyUSB0`、把雷达驱动的 ROS context 拆掉，典型报错是**先刷一串 `Check Sum 0x… != 0x…`，随后 `terminate called … RCLError: could not create publisher: rcl node's context is invalid` → 驱动 `exit code -6`**。排查与清理：

    ```bash
    ps -eo pid,etime,args | grep -E "slam_toolbox|robot_bringup|ydlidar" | grep -v grep   # 看有没有两份
    sudo fuser -v /dev/ttyUSB0        # 串口应当只有 1 个 ydlidar 进程
    kill <多余PID>;  ~/tools/nav_screen.sh kill all && ~/tools/nav_screen.sh base chassis  # 或整体重启
    ros2 topic hz /scan               # 恢复判据：回到 ~10Hz
    ```

14. **改了源码/参数"反复 build 也不生效"**（2026-09-12 实锤）：`install/` 里可能是被整树同步塞进去的旧副本，colcon 对 ament_python 会因目标文件"看起来更新"而跳过覆盖。症状=源码有该功能、`install/` 里 grep 不到、`ros2 param list <node>` 没有该参数（当年 `/imu` 一直不出现就是这个）。解 = `rm -rf build install` 后重建；判据 = 同时 grep `src/` 与 `install/` + 看运行态参数。
15. **`ekf_params.yaml` 的 `process_noise_covariance` 必须全浮点**：写成裸整数 `0`（而非 `0.0`）会让 `ekf_node` 启动即崩、`/odom_filtered` 消失（日志 `Sequence … same type` / exit -6）。改完这个文件必须重建才生效（回到坑 14）。
16. **AMCL 当前用 `DifferentialMotionModel`**：麦轮横移段的里程计模型不匹配，横移时定位可能漂（余项，见 §6）。
17. **`chassis_driver` 的 `dt=0.1` 是硬编码**：积分用的不是真实时间戳差分，高频下发时里程计幅度略有偏差（余项，见 §6）。
18. **`screen -r teleop` 报 `There is no screen to be resumed matching teleop`**（2026-09-13 实机踩到）：`teleop_twist_keyboard` 在本板是 **2.4.1**，没有 `--repeat`（那是 ROS1 的参数）——一旦按老文档写成 `--ros-args --repeat 10.0`，rclpy 就抛 `UnknownROSArgsError: ['--repeat', '10.0']`、节点秒退，screen 会话随之消失（`/tmp/teleop.log` 里留的是那段 traceback）。正确起法 = 不带 `--repeat`，按住方向键让终端自动重复发键：

    ```bash
    ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -p speed:=0.3 -p turn:=0.5
    # 或 ~/tools/nav_screen.sh teleop（脚本里已改好）
    ```

19. **rosbridge 是独立会话，`kill all` 会把它一起停掉、且不会自动回来**（2026-09-13 实锤：Foxglove 报「无法连接 ws://100.65.82.93:9090」，查下去是 9090 上什么都没有）。三步排查：`screen -ls` 有没有 `lat` → `ss -ltnp | grep 9090` → `tail /tmp/lat.log`；补起用 `~/tools/nav_screen.sh lat`。**真连上的判据**＝lat.log 里出现 `[Client …] Subscribed to /map /scan /amcl_pose`（本机可 `Test-NetConnection 100.65.82.93 -Port 9090` 复核 TCP）。

20. **发目标前先核对地图有效范围**（2026-09-13 实锤）：目标略微越界（`my_map3` 上边界 y=3.97，目标 y=4.0）就会被 planner 判 `off the global costmap`，规划必失败 → 恢复行为空转 → **status=6（ABORTED）**。算范围与读法见 §3.6。
