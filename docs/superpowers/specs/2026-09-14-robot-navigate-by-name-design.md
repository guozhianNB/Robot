# 语音「指哪到哪」设计（老人说地名 → 小车直接前往）

> **目的：** 老人对着车说「带我去护士办公室」，车直接开到那儿，到了说话告诉老人；中途喊停立刻停。
> **状态：** 设计定稿待评审（未开工）。
> **日期：** 2026-09-14
> **用户决策（2026-09-14，原话）：**
> - 「目前先实现老人在车上直接说，小车就能直接直接前往目的地。带急停。等后面用户系统完善后再改进。老人可以直接对小车说"带我去护士办公室"」
> - （问"要不要多问一句"）「**一律直接走，不需确认**。后续会有用户分层权限系统设计」
> **顺序：** 本文档是**第二期**，依赖第一期《地图编辑器》`2026-09-14-map-editor-design.md`（`destinations` 表、`roslink.py`/`locator.py`）。第一期先落地，本文档再做。

## 一、目标与验收

**目标：** 老人一句话，车自己走过去；不想去了喊一声就停。

**验收标准：**

1. 老人对车说「带我去护士办公室」，车**当场播报"好，带您去护士办公室"并出发**（不是等到开到了才出声），无需二次确认。
2. 到达后**主动播报**「到了，护士办公室」；失败播报明确原因（如"那个地方我够不着"）。
3. 导航途中老人说「停下」，**1 秒内**车停、播报「好，停下了」。
4. 老人说了个没教过的地名（如"停车场"）→ 车回「我不知道停车场在哪，我认得：护士办公室、客厅…」，**不发任何运动指令**。
5. rosbridge 没起 / 导航栈没起 / 目标越界 → 工具返回失败并如实播报，**绝不假装成功**。
6. 没有地图编辑器接口、没有 ROS 环境时，全部逻辑可用假位姿/假服务在 Windows 上单测。

## 二、范围

### 2.1 本轮做

| 能力 | 说明 |
|---|---|
| 地点解析 | 「带我去 X」「去 X」「X 在哪，带我去」→ 归一成 `destinations` 里的标准名（先精确匹配，再别名匹配） |
| 直接导航 | 查表得 `(x, y, yaw)` → 经 rosbridge 调 `/robot/navigate_to` → 阻塞等结果 |
| 出发播报 | "好，带您去 X"（既是交互反馈，也是给老人的打断窗口） |
| 到达/失败播报 | 成功后播报；失败播报原因 |
| 前置安全校验 | 地点存在且在允许清单内 / 边界余量 ≥0.3m / 忙时拒绝（§4） |
| 急停（三入口） | ① ASR 文本关键词短路 ② LLM 工具 `robot_stop` ③ 底盘自身急停。见 §5 |
| 状态工具 | `robot_where_am_i`（我在哪 + 边界余量）、`robot_status`（是否在动） |

### 2.2 本轮明确不做

| 不做 | 说明 |
|---|---|
| **二次确认** | 用户明确"一律直接走"。《分层用户体系》规格 D5/D11 的二次确认状态机**本轮不做**，留给后续权限系统重启；地点的 `risk` / `elder_allowed` 字段先由第一期编辑器填好、本期只消费 `elder_allowed` |
| 多目标巡逻（"去 A 再去 B"） | 现有服务是单目标阻塞式；序列导航等本期跑通后再加 |

| 自动回充 / 低电量联动 / 障碍上报联动 | 目前没有 `robot/battery`、`robot/obstacle` 话题 |
| 管理台/远程页面发导航目标 | 本期只做车载语音这一个入口 |
| 走出地图范围的长距离任务 | 三张图覆盖都不够，先跑熟室内 |

## 三、架构与数据流

```
老人说话 ─▶ 唤醒/ASR（现有 voice 链路）─▶ 【急停短路】命中停词且车在动 ─▶ 直接 /robot/cmd_stop（不进 LLM）
                                     └─▶ 未命中 ─▶ chat_stream 工具循环
                                                     └─▶ robot_goto("护士办公室")
                                                             ├─ 查 destinations（第一期表）
                                                             ├─ 前置校验（§4）
                                                             ├─ 发目标**立即返回**（不阻塞，§6.2）
                                                             │      └─ roslink ─▶ rosbridge:9090 调 /robot/navigate_to
                                                             └─ 返回"已出发" ─▶ LLM 说「好，带您去护士办公室」─▶ TTS

  后台导航监控（§6.3）──订阅 /robot/exec_state、/robot/arrived──▶ 到达/失败 ─▶ 主动播报「到了，护士办公室」
```

- **通道选型：rosbridge（websocket），不用 MCP。** 理由：① 第一期已因"车在哪/地图指纹"建立 `roslink.py`，动作下发复用同一条连接即可；② `LLM/car_mcp` 是 stdio 子进程 + rclpy，**必须和 ROS 同机**（Windows 开发期起不来），而 rosbridge 是网络客户端，开发期就能连板卡真机联调；③ 板卡上 rosbridge 已在跑（`~/tools/nav_screen.sh lat`）。
- 与《分层用户体系》规格 §7.2 的差异：那里把 `robot_goto` 规划在 car MCP 内（P1 暂缓）。本设计改为 **LLM 侧本地工具 + rosbridge**，需回填该规格（见 §9）。
- 车端**零改动**：`robot/navigate_to` 的 `x/y/theta` 分支已实测可跑；`place` 分支继续闲置（地名→坐标的唯一真相在 LLM 侧的 `destinations` 表）。

## 四、前置校验（LLM 侧安全层，必做）

| # | 校验 | 不通过时 |
|---|---|---|
| 1 | 地点在当前地图的 `destinations` 中存在（精确或别名命中） | 拒绝 + 播报可用地点清单 |
| 2 | `elder_allowed = 1`（第一期的唯一闸门） | 拒绝 + 「那个地方我不能自己去」 |
| 3 | 目标在地图有效范围内、各边余量 ≥ `map_boundary_margin_m`(0.3m)（复用 `where_am_i.py` 口径） | 拒绝 + 「那个位置我够不着」（实测越界 3cm 就会 `ABORTED`，提前拦住） |
| 4 | 车当前空闲（`/robot/exec_state == idle`） | 拒绝 + 「我正在去 X 的路上」 |
| 5 | 地点绑定的 `map_name` 与当前识别到的地图一致 | 拒绝 + 「地图对不上，得先重新定位」 |
| 6 | rosbridge / 导航栈可用（`navigate_to_pose` action 存在） | 工具返回 `ok:false` + 原因，不假装成功 |

> 校验 5 依赖第一期的"当前地图自动识别"（`/map` 元数据指纹）。若识别为 `unknown`，则降级为**仅告警不拦截**（避免因识别失败把功能整体卡死），并把该情况写审计。

## 五、急停（三入口，其中两个是本期新增）

**现状（实测代码）：** `worker.py` 的 barge-in **只停音频、不停车**；待机时喊停要走 ASR 出句 → LLM → 工具调用，**延迟数秒**——老人喊"停"时车还在走，这是本期必须补的洞。

### 5.1 入口一：ASR 文本关键词短路（本期新增，最快）

- `conf.ESTOP_KEYWORDS = ["停", "停下", "停车", "别动", "别走", "不要走", "急停", "站住", "别去了", "我不去了", "等等"]`；
- 在 **ASR 最终文本**上先做短路判断，命中则：发 `/robot/cmd_stop` → 播报「好，停下了」→ **不把这句话送进 LLM 工具循环**（快且省）；
- **防误触发（关键）**：仅当 `/robot/exec_state != idle`（车真的在动）时才短路。车静止时老人说"停下来想了想"这类话照常走对话，不会被当成急停——否则聊天里出现"停"字就会触发。
- 短路不依赖 LLM/网络，rosbridge 断线时仍要走一次"试图发急停"并把失败写审计（不能静默）。

### 5.2 入口二：LLM 工具 `robot_stop`

- 工具形态已有先例（`car_mcp` 的 `robot_stop`）；本期在 LLM 侧本地工具里加同名工具，走 roslink 发 `/robot/cmd_stop`；
- 触发场景：老人说"先别去，我忘了拿东西"这类需要语义理解的话（关键词表覆盖不全时由工具兜底）。

### 5.3 入口三：底盘/硬件自身急停

不在本设计范围（协议与固件层已有 `cmd_stop` 与看门狗），本期只保证 LLM 侧不拦截、不覆盖。

### 5.4 导航中被打断（本期决策）

**导航进行中一旦发生 barge-in（老人插话），立即停车**，播报「停下了，您说」。

- 理由：车在动时，安全优先。误伤代价 = 老人一句"哦"导致停下，重说一次即可；不停车的代价 = 老人喊停却继续走。
- 车静止时的 barge-in 行为不变（仅停音频）。

## 六、工具契约与导航时序

### 6.1 工具（LLM 侧本地工具，`LLM/tool/robot_nav.py`，`@tool` 自动注册）

| 工具 | 参数 | 返回（JSON 字符串） |
|---|---|---|
| `robot_goto` | `destination: str` | 受理：`{ok:true, status:"started", place, x, y, yaw, message}`；拒绝：`{ok:false, status:"rejected", error} ` |
| `robot_stop` | — | `{ok, message}` |
| `robot_where_am_i` | — | `{ok, x, y, yaw, clearance_m, map_hint}` |
| `robot_status` | — | `{ok, exec_state, moving, place}` |

- 工具名沿用已有约定（`robot_*`），与 `car_mcp` 同名时**本地工具优先**（`tools.py` 既有规则）；本期建议不再把 car MCP 当生产路径，故不构成冲突。

### 6.2 为什么导航必须异步（关键设计决策）

同步阻塞等到达是**错的**，有两个硬伤：

1. **播报时序崩了**：若工具在 `navigate_to` 返回前阻塞，`chat_stream` 这段期间产不出 `content`，老人要等到**车都开到了**才第一次听到声音——全程无反馈；
2. **超时链不匹配**：单次导航车端最多 180s（`robot_actions.py::_await_goal`），而 `conf.LLM_TIMEOUT = 60`，阻塞式调用会被上游先掐断，而车还在走。

因此 `robot_goto` **只负责"受理"**：校验通过 → 调服务发目标 → 立即返回 `status:"started"`，让 LLM 当场说出「好，带您去护士办公室」。行程中的到达/失败由后台监控驱动（§6.3）。

### 6.3 后台导航监控与主动播报

- 新增后台监控（常驻线程/任务，随 `lifespan` 启动，命名 `LLM/nav_watch.py`）：订阅 `/robot/exec_state`、`/robot/arrived`，维护"当前导航任务"状态；`robot_goto` 受理时登记任务、`robot_stop` 或急停时清除；
- 到达/失败 → **主动播报**，复用现成入口 `voice_api.begin_text_reply(settings)` + `feed_text_reply(handle, delta)` + `end_text_reply(handle)`（2026-09-13 kiosk 文本播报批次已并入 main，无须新造通道）；
- 播报文案：到达「到了，护士办公室」；失败「去不了，<真实原因>」；
- 不抢话：老人正在说话或正在播报时，到达播报**排队等当前轮结束**（沿用现有状态机语义）；
- 降级：语音链路不可用（TTS 降级/未启用）→ 只写对话历史并推 bus 事件，kiosk 气泡显示，不报错；
- `robot_goto` 受理后若监控发现 `exec_state` 长时间停在 `navigating` 而 `arrived` 从未来 → 按车端 180s 超时口径播报「路上卡住了，我先停下」；
- 播报文案由 LLM 依返回结果生成，但**失败必须播报真实原因**（提示词里写死这条红线）。

## 七、错误处理与降级

| 情况 | 行为 |
|---|---|
| rosbridge 未配置/连不上 | 工具返回 `ok:false` + 「导航服务连不上」；查询类接口 `{"ok": True, "status": "unavailable"}`；后端照常运行（AGENTS 稳健性） |
| `navigate_to_pose` action 不存在（导航未启动） | 明确返回「导航模式没启动」，不进入"发送中"假状态 |
| 导航中目标被拒绝（地图外/障碍内） | 播报「那个位置我去不了」，并提示可在编辑器里检查该点 |
| 中途急停 | 车端返回 `收到急停，已取消导航`；LLM 播报「停下了」并置空闲 |
| 超时（180s） | 播报「路上卡住了，我先停下」（并确保发一次零速/急停） |
| 工具抛异常 | 异常吞掉防崩后端 + 写审计 + 返回 `ok:false`（AGENTS 错误处理约定） |
| 事件同步 | 本期复用现有 `tool_start`/`tool_result` 事件即可，**不新增 SSE 事件类型**（避免动 `frontend/packages/shared/src/events.ts` 这个唯一事实来源） |

## 八、测试与验收

**无 ROS 环境（Windows，主力）：**

1. 地点解析：精确名 / 别名 / 未知 / 多条候选；
2. 六条前置校验逐条（含"越界 3cm 被拒"）；
3. 关键词短路：车在动 → 短路且不调 LLM；车静止 → 不短路、正常走对话；
4. rosbridge 假客户端：服务调用成功 / 返回失败状态 / 超时 / 连不上，四条路径的返回值与播报文案；
5. `exec_state != idle` 时的忙时拒绝；
6. 工具装配：`/api/tools` 能看到新工具、开关生效、审计落 `tool_log`；
7. 后台监控（`nav_watch`）：注入假 `exec_state`/`arrived` 序列 → 受理 → `navigating` → `arrived`，验证只播报一次「到了」；注入"长时间 navigating 无 arrived" → 验证超时播报；
8. 不抢话：模拟"正在播报中到达" → 播报排队而不是插断；
9. 语音链路不可用（TTS 降级）→ 到达只写历史 + 推 bus 事件，不抛错、后端不受影响。

**板卡真机（需现场安全确认后）：**

10. 起 base + navigation + rosbridge，AMCL 对齐初始位姿；
11. 对车说「带我去护士办公室」→ **当场出声**、车出发、到达后主动播报「到了」；
12. 途中说「停下」→ 1 秒内停住；
13. 说一个没教过的地名 → 被拒且车不动；
14. 拔掉 rosbridge（`kill lat`）后重试 → 后端不崩、播报如实失败。

## 十一、动手前的前置条件

1. **第一期《地图编辑器》已落地**（`destinations` 表 + 地点已标好；否则要用 CLI 手工填几个点才能测）；
2. **重扫一张地图**（现有三张未知率 60.7%~85.1%，覆盖不够）；
3. **AMCL 初始位姿对齐**（板卡实测 `/amcl_pose` 恒在 `(0,0,0)`，不对齐则地点坐标全错）；
4. 板卡 rosbridge 在跑（`ss -ltnp | grep 9090` 复核；`kill all` 后它不会自动回来）。
