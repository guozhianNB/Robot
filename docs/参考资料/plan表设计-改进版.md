# 小车「计划表」设计（完整版 · 改进稿）

> 这份文档从 `docs/参考资料/plan表设计`（你的手稿）出发，把它补成一份能开工的完整方案。
> 尽量用大白话写，不堆术语；凡是绕不开的词，后面都跟一句解释。
> 里面所有例子都还用你手稿里的那几个（A 房间、护士站、老人摔倒、讲新闻、闲逛）。
>
> **一句话总览：** 给小车加一本「待办本」——它自己写、自己做、自己能划勾，被别人插队后知道该不该回来接着干，重启之后不会以为自己还在半路上。

## 〇、你的想法哪里对，哪里要补

**你已经想对的三件事：**

1. **一次对话的结束 ≠ 一件事的结束。**「去 A 房间看看有几个人，再回护士站汇报」这件事要跑好几分钟，而现在小车只在一次对话里连做几步就收摊了。需要有东西把「还没干完的事」记在对话之外。**这就是计划表存在的根本理由。**
2. **有不同的活儿同时来，就得排先后。** 摔倒汇报是 P0、讲新闻是 P2、闲逛是 P3——这个层次的直觉是对的。
3. **计划要能当场改。**「拍到墙 → 先转转身」这个例子是整个设计里最有价值的一条，也是小车和「照着固定脚本演」的区别。

**要补的五件事**（下面第二～第八节逐条展开）：

| # | 要补的 | 一句话 |
|---|---|---|
| 1 | 等级定得不对 | 「紧急」和「重要」不能在同一把尺子上比大小；救命的事不该由模型自己判 |
| 2 | 少了「什么时候才建计划表」 | 不然「现在几点」也会生成一张表，待办本几天就撑爆 |
| 3 | 状态的符号不够用 | 缺「失败」「取消」「等人」；而且 `*` 的意思其实是「被顶了」，不是「没做完」 |
| 4 | 「打断」是三件事混在一起 | 停下手上的活 / 排队等 / 嘴上说「现在不行」——要分开，而且得有人管着「车只有一辆」 |
| 5 | 没说重启之后怎么办 | 不写清楚，就会出现「小车以为自己还在去护士站的路上」 |

## 一、两个本子分工：小本子干活，大本子记事

| | 小本子（现在已有的能力） | 大本子（要新增的：计划表） |
|---|---|---|
| 管什么 | 一次对话里，**怎么把手上一件事做出来** | **要办哪些事、先办哪件、被打断了怎么办** |
| 活多久 | 一次对话，说完就完 | 跨对话、跨分钟，存在数据库里，重启还在 |
| 例子 | 「看看房间里有几个人」——调摄像头、发现拍墙、转个身、再看一次 | 「去 A 房间 → 看看有几个人 → 回护士站 → 汇报」 |
| 谁会改它 | 模型边做边想 | 小车自己写，也可能被新来的事顶掉 |

**为什么要分开：** 小本子的特点是「现想现做、错了马上改」，天生不适合记「我答应过老人十分钟后回来汇报」这种跨时间的承诺。反过来，大本子也不该管「摄像头这次该转多少度」这种临场细节。

**两个本子怎么配合：** 大本子上写着「第 1 步：开到 A 房间门口」。轮到这一步时，把这一步交给小本子去干（该调导航调导航、该纠错纠错）；干完了，在大本子上把第 1 步划掉，再看第 2 步。**大本子管「做什么」，小本子管「怎么做」。**

## 二、等级怎么定（改进后的 P0 ~ P3）

**你的原稿：** P0 最重要/重大、P1 紧急、P2 重要、P3 一般。

**问题在哪：** 数字越小越优先，可「紧急」和「重要」本来就是两把不同的尺子。放在一把尺子上量，模型每次判级都会飘——同一件事，今天判 P1，明天判 P2。而且「老人摔倒」这种**要命**的事和「讲新闻」这种**意愿**的事被放在同一个排行榜上比大小，本身就不太稳妥。

**打比方：** 医院分诊不会问「谁的事更重要」，而是按顺序问三句：**有没有生命危险 → 谁在等着、等不及 → 谁先来的**。照这个思路改：

| 级别 | 什么意思 | 例子 | 谁能定这一级 |
|---|---|---|---|
| **P0 救命级** | 有人可能受伤，或正在受伤 | 老人摔倒、喊救命、SOS 告警、卡在门口 | **后端自己认**：听到「摔倒/救命/不舒服」这类词，或告警链路一响，直接定为 P0。模型只能往上提，**不能往下压** |
| **P1 急着要** | 老人当面明确要求，且不能拖 | 老人按了呼叫、说「快带我去厕所」 | 模型可以报，后端可以往上提 |
| **P2 一般请求** | 老人的正常要求，不急 | 「带我去护士站」「给我讲讲新闻」 | 模型 |
| **P3 自己找活** | 没人要求，小车自己安排的 | 巡逻、闲逛 | 后端 |

**三条规矩：**

1. **同级别，先来先做。**
2. **P0 压所有人，不需要商量。**
3. **「停下」不算一个级别，它是一个随时生效的开关。** 不管小车在忙什么、计划表上排着什么，听到停就停。

## 三、什么时候才建计划表（这道门槛必须有）

**不设门槛会怎样：** 你问「小车，现在几点」，它认认真真建一张 P3 表、做完划掉。几分钟后待办本里全是这种一行字的废表，小车自己也理不清哪些事是真答应了人的。

**建议的门槛 —— 满足下面任意一条，才建计划表：**

1. **要等时间或等人。** 例：「带我去护士站」要先等老人说「准备好了」。
2. **要出门跑一趟，而且不止一步。** 例：「去 A 房间看看有几个人」至少包含「过去」和「看」两步，中间车要动。
3. **老人等着结果，但一次对话里做不完。** 例：「去看看，回来告诉我」。

**不建表的：** 聊天、查天气、讲新闻、「现在几点」、一次调用就能搞定的事——这些当普通对话处理就行。

**倾向性：宁可漏建，不要乱建。** 漏建了顶多是这件事没被记下来（也就几分钟的事）；乱建了是待办本被撑爆，小车分不清轻重，反而更糟。

> 具体数字我给了个默认值：**预计 30 秒内能做完的，不进计划表。** 这个数可以调，见第十四节。

## 四、一条计划表长什么样

### 4.1 整条计划要记的东西

| 记什么 | 大白话 | 例子 |
|---|---|---|
| 编号 | 第几号计划 | P0-12 |
| 级别 | P0 ~ P3 | P0 |
| 标题 | 一句话说明白要干嘛 | 汇报老人摔倒 |
| 步骤清单 | 要一步步做的事 | 见下 |
| 现在在做第几步 | 一眼看出进度 | 第 3 步 |
| 要不要回谁的话 | 老人问了、得给个交代 | 回张三：「现在不行，等会儿就来」 |
| 能不能被插队 | 让不让别人插到前面 | 只有 P0 能让它让路 |
| 什么时候算做完 | 不是最后一步做完就算，还得把话回了 | 汇报完 + 护士回应了 |
| 什么时候算废 | 超时 / 老人改主意 / 车坏了 | 超过 10 分钟没进展就作废 |

### 4.2 每一步要记的东西

| 记什么 | 大白话 | 例子 |
|---|---|---|
| 序号 | 第几步 | 1 |
| 干什么 | 一句话 | 开到 A 房间门口 |
| **哪种步** | 「动手的」还是「还要再琢磨的」 | 动手的 |
| 状态 | 见 4.3 | 已完成 |
| 交给谁干 | 具体哪个动作 | 导航到「A 房间门口」 |
| **怎么算做成了** | 不能光听模型说 | 车**真的到位了**（导航自己报成功），不是模型说「到了」就算 |
| 搞砸了怎么办 | 重试、跳过、还是整条重来 | 重试 1 次，还不行就改计划 |

**「哪种步」为什么要分两种（这条很重要）：** 你手稿里的一行「调用工具，前往 A 房间门口」是**动手的**——直接对应一个动作，做了就是做了。而「看看房间里面有几个人」是**还要再琢磨的**——它自己还得先规划怎么才能看到人（调摄像头？先转头？）。两种混在一行里，负责推进的机器就不知道拿它怎么办。
**规矩：动手的那一步必须绑一个具体动作，并且有机器能自己验的成败标准。** 像「看看有几个人」这种，要么往下拆成能动手的步，要么明确允许它再展开一层（但只允许一层，别套娃）。

### 4.3 状态符号（保留你手绘的记号）

| 符号 | 名字 | 大白话 |
|---|---|---|
| `x` | 已完成 | 干完了 |
| `>` | 正在做 | 现在就在干这个 |
| `-` | 还没做 | 排队等着 |
| `*` | **被顶了** | **不是「没做完」，是「先不做了／被新步骤顶到后面了」** |
| `✗` | 失败 | 试过了，没成 |
| `⊘` | 取消 | 不用做了（老人改主意，或有更急的事） |
| `⏸` | 等人／等条件 | 得等老人说「准备好了」才能往下走 |

**`*` 的含义我给你改了一下，这是必须改的：** 你原稿写的是「计划未完成，作为 plan 执行记录」。但看你自己的例子——「转转车身」插到了「看看房间里有几个人」前面，那条**不是没做完，是先让路、等会儿还要做**。
「没做完」和「被顶掉」是两回事：一个要记得回头补，一个可能永远不做了。混在一个符号里，小车就分不清该不该回头。

## 六、被插队怎么办（这是完整版最核心的一块）

**先说清楚：你手稿里的「打断」其实是三件不同的事。**

| 你写的 | 实际是什么 | 该怎么处理 |
|---|---|---|
| 「P2 打断 P3 闲逛」 | 小车正在干的事要**停下** | 决定：回头接着干，还是直接作废 |
| 「P0 抢占讲新闻」 | 讲新闻**暂时做不了**，不是动作被抢 | 排队，等 P0 忙完再说 |
| 「回复老人现在还不行」 | 只是**嘴上给个交代** | 不属于调度，属于回话 |

### 6.1 三种插队做法，选一种执行

| 做法 | 什么意思 | 什么情况用 | 例子 |
|---|---|---|---|
| **做完再回去接着干** | 记住断点，忙完回来继续 | 被顶掉的事还有价值，且断点说得清 | 小车正擦着桌子，被叫去送药；送完回来接着擦 |
| **顶掉就作废** | 不回头了 | 回头继续没意义 | 闲逛 |
| **排队等** | 手上不停，新事等着 | 新事不急 | 讲新闻，等 P0 忙完 |

### 6.2 谁能插谁的队（默认规矩）

| 情况 | 做法 |
|---|---|
| 任何事被 **P0** 顶 | 立刻让路；如果车正在移动，**立刻停** |
| P3 被 P2 / P1 / P0 顶 | **作废**（闲逛、巡逻这类回头补没意义） |
| P2 被 P1 顶 | 让路（具体见第十四节的一个待定问题） |
| P2 和 P2 撞上 | **排队**，先来先做 |
| 同级别 | 先来先做 |
| 「停下」 | **不排队，任何时候都能直接执行** |

### 6.3 车只有一辆：排队机

计划表可以有十张，但车只有一个身体。所以要有**一个专门管排队的人（后面叫「车队长」）**：

- 所有会让车**动**的事（开过去、转个身），都得找车队长要许可，一次只放行一件；
- 不许两张计划表同时给车下「往前走」和「往左转」——车会听两个口令，动作打架；
- 「停下」是唯一例外：**不找车队长、不排队，谁说都算，立刻执行**。

## 七、计划会当场被改（这一步是你设计里最关键的地方）

**你举的例子就是标准做法：** 摄像头拍到墙 → 不删「看看有几个人」，而是在它前面插一步「转一转车身，检查车身摆正没有」。

**两条硬规矩：**

1. **插步骤不许偷偷把原来那条抹掉。** 原来那条改成 `*`（被顶了），新的步骤另外加。这样以后查问题时能看出小车当时绕了什么弯。
2. **「做成了没有」不能光听模型说。** 这是最容易出事的地方：画面拍的是墙，模型也可能汇报「我看到了 3 个人」。
   → 所以每一步都要有一条**机器自己能验的硬指标**（比如：画面里确实有人形、画面不是一堵墙）。不达标就记「失败」，然后触发改计划——而不是直接划勾。

## 八、重启之后怎么办（不然会有「幽灵计划」）

小车断电、后端重启之后，待办本里的计划不能一视同仁：

| 级别 | 重启后 |
|---|---|
| P0 / P1 | **捞回来接着做。** 如果已经太晚了，就补报一句「刚才那件没做完的事，已经过了」（沿用现在吃药提醒「错过补报」的做法） |
| P2 / P3 | **直接丢掉**，不补 |

**理由：** 救命的事不能因为重启就消失；但绝不能让小车重启之后以为自己还在去护士站的路上、还在给谁讲新闻。

## 九、关于「多张计划表 / 巡逻专用表」

**你原稿：** 给巡逻任务准备一张专门的巡逻计划表，按任务类型选表。

**我的建议：不做固定模板。** 理由很实在：巡逻要去的房间、每个房间的状态、老人今天在不在，都会变。固定模板很快就会和现场对不上，还容易让小车照着旧表硬走一遍。

**改做「生成器」：** 给一份房间清单和顺序，**当场生成**一张计划表；巡逻中情况变了就按第七节改。这样做的效果和你要的一样（巡逻有自己的计划、能排优先级），但不会因为模板过期而跑错。

## 十、老人和护士能看到什么

- **车上屏幕（kiosk）和护士台（admin）都能看到「小车现在在忙什么」**，就用一句人话，不是整个待办本。比如「正在去护士站汇报」。
- **老人问「你干嘛去」**，小车照当前计划回答：「我正去护士站跟护士说点事，说完就来。」
- **给模型看的也只有一小段**：当前这条计划的名字 + 现在第几步 + 下一步是什么。不给全部历史步骤——既省 token，也不容易让它把以前的事拿出来乱说。
- 进度变化**走现在已有的事件通道推给前端**（和提醒、告警同一条路），前端的「事件名称表」要跟着登记一下（这是本项目的既有约定，漏了前端会收不到）。

## 十一、和现在已有的东西怎么接

| 现有的东西 | 和计划表的关系 |
|---|---|
| 一次对话里现想现做（小本子 / ReAct） | 计划表里「动手的那一步」实际干活时还是用它，不另写一套。**注意**：不是每一步都去问模型——只在「要开工」和「一步做完、要决定下一步」这两个点问模型，中间的执行完全靠机器自己跑（否则每几秒烧一次模型，又慢又费） |
| 吃药提醒 | 提醒是「到点响」，计划表是「要办的事」。提醒响了之后可以顺手生成一条计划（去房间 → 播报 → 等老人确认）。**两边不要各写一套状态**，提醒只负责「喊开工」 |
| 指哪到哪（导航） | 计划表里「开到某地」这一步直接用它，不重写。**插队能不能做成，取决于导航能不能被打断**——现在它是「一次只去一个地方、中途不接活」的，排在后面的改造里 |
| 数据存哪 | 存进 `LLM/data/brain.db`（和小车其它运行数据放一起）。**不要放进地图文件夹**——地图文件夹只放地图和「哪间是什么房间」，那是能整个拷走的一套资产；计划表是临时状态，不属于资产 |
| 急停 / 呼救 | 优先级最高的例外，永远不排队、不被挡住，和现在一样 |

## 十二、分成五步做（每一步都能单独验收）

| 步骤 | 做什么 | 做完能看到什么 |
|---|---|---|
| **1** | 把两个本子的分工和「什么时候才建计划表」定成规矩 | 还看不出变化，但后面所有实现按这份规矩来 |
| **2** | 待办本落地：存哪、怎么建、怎么一步步推进、重启恢复规则 | 说一件事，待办本里出现一条计划，能被推进到做完 |
| **3** | 排队机 + 三种插队做法 + 急停例外 | 摔倒告警能立刻插队，闲逛被顶掉；喊停随时停 |
| **4** | 改成：插步骤、标「被顶了」、失败判定，让模型在这两点介入 | 拍到墙会自己加一步「转车身」，且留下痕迹 |
| **5** | 让护士和老人看得到：屏幕显示 + 事件推送 + 给模型的那一小段 | 护士台能看到小车在忙什么，问它「干嘛去」答得上来 |

## 十三、怎么算做成了（验收）

1. 说「去 A 房间看看有几个人，再回来告诉护士」→ 车上出现一条计划，一步步划勾，回来汇报完自动收尾。
2. 中途画面拍到墙 → 计划里多出一条「转车身」，原来那条标成 `*`（被顶了），不是被删掉。
3. 摔倒告警时 → 小车立刻停下「讲新闻」，改去护士站；事后追问讲新闻那件事，它还记得。
4. 讲新闻在排队的时候，老人问「你干嘛呢」→ 能得到一句人话，不是「我在处理任务」。
5. 重启后端 → P0 那条还在（或补报一句），P3 闲逛那条没了。
6. 任何时候喊「停」→ 车停，不管计划表上排着什么。
