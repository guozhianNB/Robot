## 1. 我们**没有关键点**，对齐是打折的（最需要知道的一条）

**现象**：正面脸识别很准（本人实测相似度 0.92），但**侧脸/低头/歪头时分数会掉到 0.2~0.45**，
可能低于阈值被判成"不认识"。

**为什么**：正规流程要用 5 个关键点（眼角/鼻尖/嘴角）把人脸**旋转摆正**再送 ArcFace；
而我们用的检测模型 `yolov8n-face` 输出只有 `[1, 5, 8400]` = 4 个框坐标 + 1 个置信度，
**不含关键点**。现在的做法是退而求其次：把框**外扩 25%**（`FACE_ALIGN_MARGIN`）后裁成
正方形再缩放，等于"不旋转地对齐"。

**怎么办**（按性价比排序）：
1. 换**带关键点**的检测器：SCRFD（`buffalo_l/det_10g.onnx`，16.9MB，自带 5 点）、
   RetinaFace，或带 kpt 的 yolov5/v8-face，然后用 5 点做相似变换对齐（`vision/faceid.py`
   的 `align_face` 换成模板对齐即可，接口不变）；
2. 或者接受现状：产品上要求"正对机器人"（引导文案 + 检测到侧脸时不判身份）；
3. 顺带：外扩比例别乱调 —— 实测同一张脸 margin 0.10 与 0.40 的余弦只有 **0.514**，
   而 0.25 与 0.40 有 **0.777**。比例差太多会把背景/头发拉进输入，分数自然掉。

## 2. 红外/夜间几乎一定会掉识别率

**现象**：白天正常，夜里用 22pin 红外摄像头时可能"检得到脸、认不出人"。

**为什么**：ArcFace 系列都是在**彩色**人脸数据上训练的，红外出的是灰度图 + 低纹理 +
不同成像特性；跨模态是已知难点（不是参数没调好）。

**怎么办**：
1. 产品逻辑上明确：夜间**只做"有人"检测/防跌倒**，不切换用户（保留当前 uid）；
2. 若必须夜间识别人：单独用红外数据微调/训练一个小模型，或改用彩色+红外双模并做融合；
3. 无论哪种，**红外下的阈值必须单独标定**（见第 3 条）。

## 3. 阈值必须用自己的数据标定，换模型/换摄像头都要重标

**现象**：抄来的阈值（0.4 / 0.5）在本机可能"该认的不认"或"把别人认成你"。

**为什么**：余弦相似度的绝对值取决于"模型 + 摄像头 + 光照 + 对齐质量"，模型一变分布就变。
本机实测（`arcface_mbf`，PC 摄像头 + 公开测试图）：

| 情形 | 余弦相似度 |
|---|---|
| 同一个人（同一张脸不同裁剪） | **0.514 ~ 0.777** |
| 同一个人（真实摄像头连续帧 vs 已注册样本） | **0.93**（好帧）/ 0.66（一般）/ **0.20**（扭头那帧） |
| 不同的人（合影里两两比） | **0.137 ~ 0.386** |
| 人脸 vs 无脸纹理图（负对照） | 0.093 |

→ 同人最低 0.514、异人最高 0.386，**留白 0.128**，中点 0.450 就是 `FACE_MATCH_THRESHOLD`
默认值的来源。留白 < 0.1 就说明该换模型或改拍摄条件了。

**怎么办**：
1. 用**你们自己的人**（几位老人 + 几位护士）各拍 5~10 张，统计"同人分数分布"与
   "异人分数分布"，取两条曲线的交叉点（或按可接受的误认率选点）；
2. **两道闸门都要设**：绝对阈值 `FACE_MATCH_THRESHOLD` + 与第二名的差距
   `FACE_MATCH_MIN_MARGIN`（默认 0.03）。养老场景里"两位老人长得像"很常见，
   差距太小就宁可不认（`reason="ambiguous"`）；
3. 关注指标 **TAR@FAR**：把"误认率 FAR"压到可接受（例如 1e-3）时，"认对率 TAR"还剩多少；
4. 换检测器/对齐方式/摄像头/模型变体（mbf↔r50）→ **重新标定**，别沿用旧值。

## 4. 检测输入尺寸别盲目调大（实测反例）

**现象**：把检测输入从 640 调到 1280，远处的人反而检不到了。

**为什么**：模型是在 640 尺度上训练的，输入整体放大后画面里人脸尺寸偏离训练分布，
且 letterbox 补边占掉大量像素。

**实测**（两个人同时在画面，**同一批缓存帧**）：

| 输入尺寸 | 结果 | 单帧耗时 |
|---|---|---|
| **640（默认）** | 16/16 帧**都检到 2 人** | 203 ms |
| 1280 | 6/6 帧**只检到 1 人**（不是框被合并，是远处那位漏检） | 525 ms |

**怎么办**：保持 `FACE_DETECT_IMGSZ=640`。真要提升远处小脸检出率，正确做法是
**"先检大范围 → 把可疑区域裁出来放大再检一次"**（crop-and-zoom / 两级检测），
而不是把整幅输入放大。

## 5. 单帧结果永远不能用来切用户

**现象**：如果按单帧就切主体，会出现"有人路过就切走""老人一扭头身份就丢"。

**为什么**（本机实测）：单人测试 **15 帧里有 1 帧完全漏检**；远处的人置信度只有 0.46~0.53；
框会随身体轻微漂移；画面里多出一个人会瞬间改变"看到几张脸"。

**怎么办**：已经实现的两层计数（`LLM/face_api.py`）——
`frames`（同一组人脸连续出现了几帧）与 `identity_hits`（同一**身份**连续稳了几帧）
分开算，`switchable` 要求"稳定 + 唯一人脸 + 身份连续 N 帧"三者同时满足。
默认 N=`FACE_STABLE_FRAMES=5`、平均置信度 ≥ `FACE_STABLE_CONF=0.60`。
**实测演示**：7 次连续探测里，第 5~6 帧因扭头导致身份丢失 → `switchable` 保持 False、
`reason="identity_unstable"`，第 7 帧恢复识别但身份连续帧数重新起算 —— 这正是想要的行为。

## 6. 性能预算：整条链一次约 0.5 秒

**实测**（PC，1280×720，含取帧 + NV12 解码 + 检测 + 识别）：

| 环节 | 耗时 |
|---|---|
| 检测（YOLOv8n-face @640） | ~190 ms 单独跑；与识别同进程时实测 **343 ms** |
| 识别（ArcFace **mbf**） | **86 ms** |
| 整轮 `/api/face/probe` | **~470 ms**（好的帧 470~650 ms，个别帧到 1.5 s） |
| 识别模型换 **r50** | 单张 **324 ms**（是本机实测，所以默认用 mbf；差 12 倍） |

**怎么办**：
1. 前端轮询 **1~3 fps** 即可（再快只会排队）；5 帧稳定 ≈ 2~3 秒，对"切换用户"这种动作足够；
2. 别在同一个进程里同时跑摄像头服务 + 后端 + 识别（本次实测三者抢 CPU 会让检测从 190ms 涨到 343ms）——
   生产上摄像头服务跑在板卡/独立进程，后端按 `VISION_HOST` 取帧；
3. 板卡上走 BPU（`onnx → hbm`）能快一个量级；**但 INT8 量化对特征向量比对检测更敏感**，
   量化后必须重标阈值（见第 3 条）。

### 6.1 "画面卡顿"要先分清是**取帧慢**还是**推理慢**（2026-09-19 补）

这两个是完全不同的问题，现象都是"一顿一顿"，但药方相反：取帧慢要降分辨率/换格式/关掉抢
摄像头的程序；推理慢**不该**影响画面（画面照样流畅，只是框滞后）。GUI（`vision_test_start.py`）
现在把两个速率分开显示：`预览 x fps   推理 y 次/秒`。

当天查出并修掉的两个真凶（都在**软件**，不是摄像头坏）：

| 真凶 | 实测 | 修法 |
|---|---|---|
| **NV12 转换用纯 numpy 全幅 float32** | 1280x720 **34 ms/帧**、640x480 10 ms/帧；`--channels 1280x720,640x480` 时每帧要 **44 ms**，直接把服务端上限压到 ~22fps，还和 YOLO 抢 CPU | 改 cv2 快路径（Y 用 `BGR2YUV_I420`，色度自己按 2x2 平均）：720p **5.8 ms**（6 倍）；`bgr_to_nv12` 两句断言锁住口径（±2） |
| **预览与推理在同一个线程里串行** | 一轮检测+识别 250~700ms → 画面每 0.25~0.7 秒才换一张（相机本身是 15~30fps） | 抓帧与推理**拆成两个线程**：预览 ~30fps，框 ~3fps 滞后；回归用例断言"1 秒内预览 +30 帧、推理 +3 次" |

另外三处顺手加固：USB 摄像头**优先要 MJPG**（不设的话很多设备默认 YUY2，720p 在 USB2 上只有
5~10fps）、`CAP_PROP_BUFFERSIZE=1`（否则 `read()` 拿的是队列里最旧那帧，画面延迟越积越大）、
取帧改用 `get_next_frame`（只在真有新帧时返回 —— 用 `get_frame` 会把同一帧反复解码到
139 次/秒，白烧 CPU，还把帧率显示成假的）。摄像头打开时会在服务日志里打一行**实际格式**
（分辨率@帧率 + FOURCC）：`[webcam] 设备 0 实际格式：1280x720 @30.0fps FOURCC=MJPG`
—— 若这里是 `YUY2` 或帧率只有个位数，瓶颈就在摄像头/USB，不在软件。

## 7. 活体检测缺失：照片能骗过系统

**现象**：拿一张老人照片对着摄像头，识别会通过（ArcFace 只比对长相，不看真假）。

**为什么**：活体（防伪）是**独立能力**，与 ArcFace 无关。

**怎么办**（正式上线前必做其一）：
1. 动作指令活体（眨眼/张嘴/转头），注册时录 2~3 帧短视频；
2. 红外/结构光/深度相机做双目或深度判活；
3. 单目静默活体模型（如 Silent-Face-Anti-Spoofing 一类），但要注意跨域效果。
另外：**切换用户这类"低风险动作"可以先不做活体，但涉及隐私数据（记忆、病例）的操作必须做。**

## 8. 隐私与合规（红线级）

**现象**：人脸照片与指纹向量都能用来"对上人"，一旦外泄无法像密码那样更换。

**怎么办**：
1. **只在本机/局域网处理与存储，不上云**；`LLM/data/*` 已 gitignore，不进仓库；
2. 指纹也是敏感凭证（存在"由向量反推人脸"的攻击），与照片同等对待；
3. 增删必须有审计（已实现：`face_enroll` / `face_delete`，落在 `LLM/data/audit.jsonl`）；
4. 提供删除接口（`DELETE /api/face/people/{uid}`），老人/家属要求删除时要能彻底删；
5. 老人知情同意 + 最小必要采集（注册只存**对齐后的小脸图**，不存整幅画面——已实现）。

### 8.1 怎么**确保**照片没被推到 GitHub（`scripts/check_privacy.py`）

**`.gitignore` 给不了这个保证**，别指望它：它只对**未跟踪**的文件生效 —— 对已经 `git add`
过的文件无效，对**历史提交**更无效（2026-09-19 实测：`LLM/data/speakers/*.npz` 就是规则写好
之前提交进去的，规则再全也拦不住，至今仍在 `origin/main` 里；同类还有 `.research_sherpa/`、
`node_modules`）。

所以要有主动检查。**一条命令**：

```powershell
python scripts\check_privacy.py          # 三条通道全查（索引 / 未忽略的未跟踪 / git 历史）
python scripts\check_privacy.py --strict # 连声纹、模型权重、node_modules 也当失败
```

它怎么认人脸样本：**不依赖路径**，凭 `face_lib.add_sample()` 的固定文件名格式
`<年月日>_<时分秒>_<微秒>.jpg/.npz`（所以 `FACE_DIR` 被重定位到仓库内任何地方都拦得住），
外加 `LLM/data/faces/` 目录、`faces/<名>.jpg|npz`、`vision.face --out` 的 `det_*.jpg`。

三条通道分别对应三种事故：① 索引 = 下次 commit 会带上的；② 未忽略的未跟踪 = 下次
`git add -A` 会带上的；③ 历史 = **已经推到 GitHub 的**。任何一条命中人脸样本 → 退出码 1。

**自动化的两道锁**：

1. `tests/test_privacy.py`（**建议一直留着**）：跑 `pytest` 就会查一遍索引+未跟踪+历史，
   还逐条验证"盘上的样本确实都被 git 忽略"。**只要 pytest 绿，就没有一张人脸照片能被提交。**
2. git 钩子（一次设置，之后每次 commit/push 自动拦）：
   ```powershell
   git config core.hooksPath .githooks     # 启用；取消：git config --unset core.hooksPath
   ```
   `pre-commit` 查索引与未跟踪（快），`pre-push` 连历史一起查（推之前最后一道门）。
   钩子会打印该怎么处理并**阻止本次提交/推送**；确认无隐私问题时用 `--no-verify` 临时跳过。

> 万一真的发生（照片进了历史）：光删文件没用，必须**清史**——
> `git filter-repo --path LLM/data/faces --invert-paths` 后强推；公开仓库还要按"已泄露"处理
> （换新样本重新录入、必要时删库重建）。细节见 `docs/log.md` 2026-09-19。

## 9. 注册质量直接决定识别率

**怎么办**（产品口径）：
1. 注册时**正对镜头、光线均匀**，提示"未检测到人脸 / 请正对镜头"（接口已能区分
   "没人脸"这种业务结果：`status:"no_face"`，见 `POST /api/face/enroll`）；
2. **每人 2~3 张、不同角度与光照**（多样本取**平均指纹**，比单张鲁棒得多；上限
   `FACE_LIB_MAX_SAMPLES_PER_UID=20`）；
3. 注册取"画面里最大的人脸"（离镜头最近=本人），避免把旁边的人录进去（已实现并有单测）；
4. 框太小（人太远）时宁可拒收 —— 太小的人脸对齐后信息量不足。

## 10. 多人同时在画面 = 歧义，不许切换

**现象**：两位老人一起站在车前时，系统不该猜。**已实现**：`count != 1` →
`ambiguous=True`、`switchable=False`、`reason="multiple_faces"`。
两人场景的 NMS 不会互相抑制（实测两框 IoU=0.0、中心间距 167~172 px），所以"两个人都能检出来"
是可靠的。

## 11. 环境与权限（开发期最容易卡住的地方）

**现象**：明明有摄像头却"检不到"/`VideoCapture` 打不开。

**已知原因**：
1. **沙箱/权限**：本项目开发沙箱默认**禁止访问摄像头设备**（表现是 `isOpened=False`，
   `--list-cameras` 误报"没有摄像头"）；需要提权运行，或确认 Windows
   隐私设置里"允许桌面应用访问相机"是开着的；
2. **摄像头被独占**：`vision/camera_server` 是摄像头的唯一持有者（设计如此），
   腾讯会议/OBS 等程序占用时打不开；
3. 板卡 RDK X5 目前**没有接摄像头硬件**（VIO 扫描所有 sensor 的 chip ID 全 0x00、
   官方样例同样失败、i2c 总线上无器件）；接上 MIPI 摄像头后需先同步板卡上的
   `vision/` 目录（板卡那份是 8-27 快照，缺 `--source`/`--list-cameras`）。

## 12. 自查清单（怀疑不准时按这个顺序排查）

1. `GET /api/face/status` → 看 `detector.available`（能不能检测）、`embedder.available`
   （能不能识别）、`camera.reachable`（能不能取帧）、`library.uids/samples`（库里有几个人）。
   三者分开报就是为了一眼看出卡在哪一层。
2. `GET /api/face/people` → 确认目标 uid 有没有样本、几张。
3. `POST /api/face/probe` 连打 5 次 → 看每帧 `faces[].identity_score` 与 `identity_margin`：
   分数高但 identity 为空 = 阈值定高了；分数忽高忽低 = 拍摄条件（角度/光线/距离）问题；
   `identity_reason="ambiguous"` = 库里有两个人分数接近。
4. 库里只有一个人时 `margin` 是 `None`（没有"第二名"可比）—— 这不是 bug。
5. 用图片快速对拍：`python -m vision.faceid --compare A.jpg B.jpg`（两张**人脸图**的余弦）。

## 13. 与"OpenCV LBPH 老方案"的对比（参考用户旧项目 `face_rec.py`）

旧项目的路线是：`ultralytics` 的 YOLOv11n-face 检测 + OpenCV 的 **LBPH / EigenFace / FisherFace**
（`cv2.face`，需 `opencv-contrib-python`）识别 —— 数据集 `<人名>/*.jpg` **训练**出 `.yml` 模型，
数据变了自动重训；`predict()` 返回"标签 + **距离**"（LBPH 阈值约 90，越小越像）。

| 维度 | 旧方案（LBPH 系列） | 现方案（ArcFace） |
|---|---|---|
| **加一个人** | 数据集加图 → **重新训练** → 存模型 | **写一张 npz 即可，无需训练**（立刻生效） |
| 依赖 | torch/ultralytics + opencv-contrib | 只要 onnxruntime + opencv（无 torch） |
| 特征 | 灰度纹理直方图 / 子空间（像素级） | **512 维深度特征**，对角度/光照更鲁棒 |
| 相似度口径 | **距离**，越小越像（LBPH ~90） | **余弦**，越大越像（阈值 0.45） |
| 大库表现 | 人数一多精度明显下降 | 上千人量级仍可用（512 维 + 点积） |
| 板卡 | 无 BPU 路径 | ONNX → `.hbm` 走 BPU |
| 从旧项目吸收的点 | 数据集布局 `<人名>/*.jpg`、画面显示名字、样本数提示 | 已落地：`enroll-dir`、`draw()` 画身份、`under_sampled` 提示 |

**结论：保留 ArcFace 路线。** "无需重训"正是它能"拍一次就记住"的关键 —— 指纹就是磁盘上的 npz，
比对时**每次都重新扫目录**，所以：① 新加的人立刻生效；② 重启后仍在（换进程照样认得出）；
③ 不需要旧方案那套"数据变了自动重训"的逻辑（那份复杂度在深度特征方案里根本不存在）。

## 14. 怎么注册与识别（现在有两条路）

**路 1：对着摄像头拍**（注册向导、无人值守）
```bash
POST /api/face/enroll        {"uid": "elder_001", "frames": 5}
```

**路 2：用现成照片**（护士手机拍的 / 浏览器上传 / 旧数据集批量导入）
```bash
POST /api/face/enroll_photo  {"uid": "elder_001", "image_base64": "data:image/jpeg;base64,..."}
python -m LLM.face_api enroll-photo elder_001 D:\照片\1.jpg D:\照片\2.jpg   # 多张
python -m LLM.face_api enroll-dir   D:\旧数据集                            # <目录>/<人名>/*.jpg
```

**识别一张图片里是谁**（不推进"连续 N 帧一致"，纯识别；用于回看/核对/离线自查）
```bash
POST /api/face/identify      {"image_base64": "...", "topk": 1}
python -m LLM.face_api identify 照片.jpg
```

**其它**：`python -m LLM.face_api people`（看库与 `under_sampled` 提示）、`delete <uid>`、
`status`；环境变量 `FACE_DIR` 可把样本库挪到别的盘（例如加密盘，或测试用的临时目录）。
`count` = 返回了几张，`detected` = 实际检出几张（`topk` 只截断返回，不改变检出数）。

## 15. 实机实测记录（2026-09-18，PC + 真摄像头）：两道门槛与"跨条件"问题

这一节是**真实数据**，比任何推理都值得参考。当天流水：注册 → 重启后端 → 连续识别 → 调门槛 → 补拍。

### 15.1 两道门槛（已落地）

切换主体（`switchable`）需要**两组独立门槛**同时满足，混成一个会出问题：

| 门槛 | 配置 | 管什么 | 失败时 `reason` |
|---|---|---|---|
| 检测框置信度 | `FACE_STABLE_CONF = 0.45` | 框"够不够可信" → 算不算**稳定出现** | `low_score` / `not_enough_frames` |
| 身份相似度 | `FACE_IDENTITY_CONF = 0.55` | 认"够不够像" → 能不能**据此切换** | `identity_low_score` |
| 进库阈值 | `FACE_MATCH_THRESHOLD = 0.45` | 是不是库里的人（+与第二名的差距） | `no_identity` / `below_threshold` / `ambiguous` |

检测门槛原本是 **0.60**，当天实测弱光/稍远时 YOLO 检测分只有 **0.44~0.53**，导致身份相似度 0.95 却
永远不给切换 → 降到 0.45，把"要不要切"的决定权交给身份分门槛。

### 15.2 同一个人，跨条件掉到 0.50（当天最重要的发现）

| 场景 | 检测分 | 身份相似度 | 说明 |
|---|---|---|---|
| 注册时（偏暗、稍远） | 0.44~0.53 | **0.95~0.97** | 识别用的帧与注册样本**同条件** |
| 同一人，换个光照/距离再识别 | **0.70~0.77** | **0.50~0.51** | 图像质量更好，但样本是"另一种样子" → 相似度腰斩 |
| **补拍 3 张当前条件下的样本后** | 0.76~0.81 | **0.87** | 平均指纹覆盖两种条件 → 恢复并超过门槛 |

**结论**：跨条件的相似度损失远大于"图像清不清晰"。所以 ——
1. **注册时就要多条件拍**（这正是 §9 的建议，本节是它的实测证据）：至少 2~3 张，最好不同光照/距离/角度；
2. 老人**换了房间/换了季节/换了摄像头**后如果识别变差，第一反应是**补拍几张当前条件的样本**，而不是调阈值；
3. `reason=identity_low_score` 就是系统在告诉你"我认出来了，但不够确定到可以动作" —— 这是**有用的告警**，不是故障。

### 15.3 当天验证通过的完整闭环

```
建档(uid=000) → 拍 5 帧 → 重启后端（库仍 5 样本，记忆落盘）→ 连续识别
→ 6/6 帧认出（相似度 0.95+）→ 补 3 张后 switchable=True（第 5 帧起）
性能：检测 0.56s / 识别 0.086~0.13s / 整轮 0.44~0.89s（三个进程同机抢 CPU）
```

### 15.4 排查口诀

`identity` 有值但 `switchable=False` → 看 `reason`：`not_enough_frames`=还没连续够；`low_score`=检测框不
可信（光照/距离）；`identity_low_score`=跨条件不像（**去补拍**）；`identity_unstable`=身份在抖（人动得
厉害/侧脸）；`multiple_faces`=画面里不止一个人；`no_identity`=库里没这个人或不像到阈值以下；
`frames_reset`=轨迹集合刚变过（画面里多了人 / 短暂丢失后重连）——"连续 N 帧"要重新数。

### 15.5 稀疏轮询下的轨迹关联（当天第二个真机坑，已修）

**现象**：识别一直正常（8/8 帧认出、相似度 0.65~0.78），但 `frames` 会在第 6 帧突然从 5 掉到 1、再 1、
再 2 —— `switchable` 刚亮就灭；而且那时 `reason` 竟显示 `ok`（明明 `stable=False`），排查时极误导。

**根因**：后端是"**轮询一帧算一帧**"（实测 ~0.8 s/轮），人在 0.8 秒里自然会挪动；而跨帧关联只用了
**IoU ≥ 0.30**，IoU 对位移/缩放极其敏感，人一晃就掉到阈值下 → 同一个人被当成**新目标** → 轨迹集合变了
→ "连续 N 帧"从 1 重新数。

**修法**（两道判据，先严后宽）：
1. `IoU ≥ FACE_TRACK_IOU`（0.30）优先 —— 连续视频帧的正常情况；
2. **兜底**：中心位移 ≤ `FACE_TRACK_MAX_JUMP`（1.0）× 人脸框短边 **且** 尺寸比在 [0.5, 2] → 仍算同一个人
   （"换了个人"通常中心很远或尺寸差很多，照样会被判成新轨迹）。
   另把 `reason` 补上 `frames_reset`，不再用 `ok` 掩盖"一致帧数被重置"。

**效果对比（同一台摄像头、同一人）**：

| | `frames` 序列 | `switchable` |
|---|---|---|
| 修复前 | 1,2,3,4,**5→1,1,2** | 第 5 帧亮，第 6 帧就灭 |
| 修复后 | 1,2,3,4,5,6,7,8 | 第 5 帧起**持续为真** |

> 教训：**"连续 N 帧一致"的关联判据必须匹配采样间隔**。视频流（33 ms/帧）用 IoU 没问题；
> 轮询式（0.5~1 s/帧）必须用中心位移/尺寸这类更宽容的判据，否则人一晃就断。

## 16. 自测方法（你自己就能跑，不需要开发在场）

工具：`scripts/face_check.py`。**建议在你自己的终端里跑**（DSH/沙箱环境访问摄像头需要额外授权，
你本地终端没有这层限制）。

### 16.1 三条命令

```powershell
# ① 只看状态（不碰摄像头）：依赖、模型、门槛、库里有几个人
python scripts\face_check.py

# ② 用图片测（不碰摄像头，最快）：这张照片里是谁
python scripts\face_check.py --photo 照片.jpg

# ③ 摄像头实测（"能不能认出我"）：自动起停摄像头服务与后端，连续探测 8 次
python scripts\face_check.py --live
#    顺手注册/补拍（会先倒计时提醒你坐好）：
python scripts\face_check.py --live --enroll 000 --frames 3
```

注册/删人/批量导入等其他操作（见 §14）：
```powershell
python -m LLM.face_api enroll-photo 000 D:\照片\1.jpg      # 用照片注册
python -m LLM.face_api enroll-dir D:\旧数据集               # 批量导入 <目录>/<人名>/*.jpg
python -m LLM.face_api people                              # 看库
python -m LLM.face_api delete 000                          # 删掉某人全部样本
```

### 16.2 输出怎么读

| 列 | 含义 | 门槛（默认） |
|---|---|---|
| 检测分 | YOLO "框得多准" | `FACE_STABLE_CONF` = 0.45 |
| **认出的是谁** | 库里最像的人，显示成 **称呼/姓名（uid）**（如 `fuze（000）`）；`未知` = 没到进库阈值 | `FACE_MATCH_THRESHOLD` = 0.45 |
| 本帧像度 | 这一帧与最像那个人的**余弦相似度** | 同条件 0.9+，跨条件可能 0.45~0.6 |
| 连续均分 | 当前"同一身份连续段"的平均相似度 | `FACE_IDENTITY_CONF` = 0.55 |
| frames | 连续几帧看到的是同一组人脸 | `FACE_STABLE_FRAMES` = 5 |
| stable | 人脸稳定出现 | —— |
| switchable | **可以据此切换主体**（唯一 + 身份稳且够像） | —— |
| reason | 没过门槛的原因 | 见下表 |

| reason | 什么意思 | 怎么办 |
|---|---|---|
| `no_face` | 没检到人脸 | 坐进画面、别背光 |
| `not_enough_frames` | 帧数还没攒够 | 保持不动多对一会儿镜头（约 3~4 秒） |
| `low_score` | 检测框置信度不够 | 开灯 / 坐近 / 别侧脸 |
| `identity_low_score` | 认出来了但不够像（**最常见**） | **补拍当前光照/距离下的样本**：`--enroll 000 --frames 3` |
| `identity_unstable` | 身份在抖 | 别晃、别扭头；稍等几秒 |
| `multiple_faces` | 画面里不止一个人 | 只留一个人（系统不猜） |
| `no_identity` | 库里没这个人 / 不像到阈值下 | 先注册；或检查是不是换了摄像头 |
| `frames_reset` | 轨迹集合刚变过 | 属正常过渡，再连测几帧即可 |
| `ok` | 全部达标 | —— |

### 16.3 三种典型结果

- **`switchable=True`**：认出且稳定，系统可以据此切换主体 —— 这是我们要的状态。
- **能认出（identity 有值）但 `switchable=False`**：最常见，看 `reason` 定位是哪道门槛；
  十有八九是 `identity_low_score` → **补拍**（§15.2 实测：补拍后 0.50 → 0.87）。
- **`identity` 为 `—`（认不出）**：相似度低于 0.45。先确认库里有这个人、且注册用的是**同一台摄像头**。

### 16.4 想真正标定阈值（推荐做一次）

只测自己一个人只能证明"能认出"，**证明不了"不会认错"**。要标定：

1. 注册 **2~3 个人**（每人 3 张、不同光照/距离）；
2. 每人再对着镜头测 5~10 次，记录**同人**相似度；
3. 让 A 站到镜头前，看系统给 B 的分数，记录**异人**相似度；
4. 取两条分布的中间值作为 `FACE_MATCH_THRESHOLD`（进库）、略高一点作为 `FACE_IDENTITY_CONF`（切换），
   并写进 `LLM/conf.py`（或用环境变量临时试：`$env:FACE_MATCH_THRESHOLD="0.5"`）。

实测参考（本机、MobileFaceNet）：同人跨条件 **0.45~0.97**，异人（公开合影）**0.14~0.39** ——
留白不宽，所以"多条件样本"比"调阈值"更管用。
